You are the lead engineer building a serious submission for the Razorpay AI Buildathon, Track 02: AI Risk Manager.

PROJECT NAME:
Reclaim Sentinel

CORE PRODUCT:
Reclaim Sentinel is an AI-powered RETURN-FRAUD VERIFICATION system for merchants.

CORE PROBLEM:
A merchant receives a return/refund request and must decide whether to release the refund. Fraudulent or manipulated returns can cause direct financial loss.

Reclaim Sentinel must verify a return BEFORE the refund is released by combining:
1. deterministic evidence verification,
2. machine-learning risk scoring,
3. historical customer/merchant return behaviour,
4. coordinated abuse-pattern detection,
5. sudden return-abuse spike detection,
6. an explainable investigation layer.

IMPORTANT PRODUCT BOUNDARY:
This is NOT a generic fraud detector.
This is NOT a generic return-risk scorer.
This is NOT a chargeback responder.
This is NOT a chatbot.

The single class of loss being addressed is:
FRAUDULENT / INVALID RETURNS THAT RESULT IN UNNECESSARY REFUNDS.

CORE DECISION:
For every return case, produce exactly one:
- APPROVE REFUND
- HOLD REFUND
- ESCALATE TO HUMAN REVIEW

The system must be conservative with money:
If evidence is insufficient or conflicting, prefer HOLD or ESCALATE rather than inventing certainty.

RAZORPAY BUILDATHON REQUIREMENTS:
- Must be a genuinely working detector/verifier, not a mockup.
- Must evaluate on a held-out test set.
- Must report precision, recall, F1 and confusion matrix.
- Must report false-positive cost explicitly.
- Must support a business-impact metric such as estimated fraudulent refund amount prevented and legitimate refund value incorrectly held.
- Must be strictly defense-only.
- No offensive security features.
- Must have graceful failure recovery.
- Must make AI usage meaningful and explain where AI is intentionally NOT used.
- Must be reproducible from the public GitHub repository.
- Do not fabricate test results. Compute all metrics from actual generated/evaluated data.

G. DECISION ENGINE
Combine deterministic evidence + ML score + abuse patterns + spike information.

Do NOT allow an LLM to directly decide whether money should be released.

H. AI INVESTIGATOR
Use an LLM only where language reasoning is genuinely useful.

The LLM should receive structured evidence from the deterministic/ML layers and create:
- concise investigator summary
- explanation of why the decision was made
- evidence supporting the decision
- missing/conflicting evidence
- recommended human-review questions

The LLM must NEVER invent evidence.
The LLM must NEVER override deterministic safety controls.
The LLM must NOT be the final money-moving authority.

If evidence is insufficient, the LLM must explicitly say:
"Insufficient evidence for an automated decision."

I. FAILURE RECOVERY
Design explicit graceful failure paths.

Examples:
- ML service unavailable
- LLM unavailable
- graph analysis unavailable
- courier/evidence source unavailable
- conflicting evidence
- malformed record

System behavior must remain safe.

For example:
LLM unavailable → decision engine still works.
External evidence unavailable → HOLD/ESCALATE rather than APPROVE blindly.
Model unavailable → deterministic safe fallback or escalation.

Record failures in an audit log.
