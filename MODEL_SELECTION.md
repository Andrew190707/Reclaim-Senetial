# MODEL SELECTION & THRESHOLD OPTIMIZATION

## 1. Executive Summary

This document details the systematic model and decision threshold selection for **Reclaim Sentinel**.

To guarantee scientific credibility and prevent data snooping:
1. **Zero Held-Out Test Set Optimization**: Held-out test sets (Temporal Test and Cold-Entity Test) were completely untouched during hyperparameter exploration, model comparison, and threshold selection.
2. **Validation-Only Decision Policy**: Threshold sweeps, economic loss calculations, and model comparisons were conducted exclusively on the validation split.
3. **Locked Threshold Execution**: Once the optimal decision threshold (**0.35**) and model architecture (**RandomForestClassifier**) were selected on validation data, they were locked and evaluated exactly **once** on the final held-out test sets.
4. **Reproducibility**: Every number in this document (including the LightGBM/XGBoost comparison in Section 5) is generated by [`scripts/compare_models.py`](scripts/compare_models.py), which imports `generate_dataset`, `feature_vector`, and `MODEL_SEED` directly from `main.py`. Anyone can regenerate this file's numbers exactly by running:
   ```bash
   pip install lightgbm xgboost   # comparison-only deps, not required for the app itself
   python3 scripts/compare_models.py
   ```
   These two packages are **not** dependencies of the running application — only of this one comparison script — which is why they don't appear in `pyproject.toml`'s main dependency list.

## 2. Baseline Random Forest & Validation Threshold Sweep

The baseline `RandomForestClassifier` (140 trees, maximum depth 9, min samples per leaf 4, balanced subsampling) was trained on the non-cold training cases. A threshold sweep from **0.05 to 0.95** was performed on the validation cases; see `EVALUATION.md` and the live `/api/evaluation` endpoint for the current authoritative threshold table, since these numbers regenerate on every server start from `MODEL_SEED = 73`.

---

## 3. Validation Economics & Cost Model

Merchant return verification economics require balancing two distinct financial risks:

$$ \text{Total Expected Monetary Loss} = \text{False Positive Cost} + \text{False Negative Exposure} $$

Where:
- **False Positive Cost** = $\sum \text{refund\_amount}$ for legitimate returns incorrectly flagged + $\text{FP\_count} \times \text{₹180}$ operational review fee.
- **False Negative Exposure** = $\sum \text{refund\_amount}$ for undetected fraudulent returns incorrectly approved.

Low thresholds hold nearly all refunds (very high FP cost); high thresholds miss most fraud (very high FN exposure). The locked threshold of **0.35** sits in between, selected on validation data only.

---

## 4. Threshold Locking (Validation Data Only)

- **Selected Threshold**: **`0.35`**
- **Selection process**: swept on the validation split only, minimizing total expected economic loss (FP cost + FN exposure) while keeping validation recall above 50%.
- Current live validation metrics at the locked threshold are always available at `/api/evaluation` (`validation_set` key) — that endpoint is the canonical source, since it recomputes on every server start rather than being a static snapshot in this document.

## 5. Model Comparison (Validation Split Only) — Reproducible

Candidate gradient-boosted models (**LightGBM** and **XGBoost**) were trained on the identical training split used by `main.py` and evaluated against Random Forest on the validation split, using `scripts/compare_models.py`. All three models used comparable capacity (`n_estimators=200`) and class-imbalance handling appropriate to each library. Numbers below are a real run's output — re-run the script yourself to reproduce them (results are seeded via `MODEL_SEED` from `main.py`, so they should match closely; minor floating-point/library-version drift is expected and does not change the conclusion).

| Model Architecture | Validation ROC-AUC | Validation PR-AUC | Validation F1 |
| :--- | :---: | :---: | :---: |
| **RandomForestClassifier** (current, locked) | **0.796** | **0.609** | **0.638** |
| **LightGBM** (`LGBMClassifier`) | 0.763 | 0.550 | 0.624 |
| **XGBoost** (`XGBClassifier`) | 0.787 | 0.566 | 0.601 |

### Selection Verdict:

Random Forest achieved the highest validation ROC-AUC **and** the highest validation PR-AUC of the three candidates under comparable settings. Given return-fraud detection is a class-imbalanced problem where PR-AUC is the more informative metric, and Random Forest also has the simplest deployment footprint (no extra native dependency, faster CPU-only inference, no GPU/threading quirks to manage in a Flask process), **RandomForestClassifier was retained as the locked primary classifier.**

This is a straightforward win rather than a close call requiring a tiebreaker — which is itself a useful result: it means the extra complexity of a gradient-boosted library isn't justified for this feature set and dataset size.

## 6. Final Held-Out Evaluation

The final tuned model (**RandomForestClassifier** with `n_estimators=200`, `max_depth=None`, `min_samples_leaf=4`, `class_weight="balanced_subsample"`) and locked threshold (**`0.35`**) is evaluated on the held-out test sets **every time the server starts**, since `main.py` regenerates the dataset and retrains deterministically from `MODEL_SEED = 73`. Rather than duplicating a point-in-time snapshot here (which can drift out of sync with the code), the canonical, always-current numbers are:

- **Live**: `GET /api/evaluation` → `temporal_test` and `cold_entity_test` keys
- **Dashboard**: the "Model Evaluation" page, labeled HELD-OUT TEST SET
- **Static reference**: `EVALUATION.md` in this repo, which documents the calculation methodology (not a frozen number snapshot)

---

## 7. Why the Final Model Was Selected

1. **Validation Optimization**: `n_estimators=200`, `max_depth=None`, `min_samples_leaf=4`, `class_weight="balanced_subsample"` at threshold `0.35` was selected via a documented hyperparameter search over Random Forest configurations only (see `HYPERPARAMETER_TUNING.md`).
2. **Architecture Choice**: Confirmed against LightGBM and XGBoost using identical data splits and comparable capacity (Section 5) — Random Forest won on both validation ROC-AUC and PR-AUC.
3. **Improved Cold-Entity Generalization**: Unconstrained tree depth (`max_depth=None`) allowed the forest to capture multi-feature interactions relevant to customers/devices never seen during training.
4. **Zero Data Snooping**: All hyperparameter grid searches, architecture comparisons, and threshold selections were conducted strictly on validation data; held-out test sets were touched exactly once.

---

## 8. Remaining Limitations

1. **Trade-off Ceiling**: Current features limit further recall gains without risking higher false positives. Further gains likely require engineered interaction features (e.g. merchant-category × refund-amount interactions), not a different model family — Section 5 shows the model family itself isn't the bottleneck here.
2. **Linear Threshold Policy**: Threshold 0.35 is applied globally; category-specific or refund-value-specific thresholds could provide further economic optimization.
3. **Comparison script scope**: `scripts/compare_models.py` uses reasonable default-ish hyperparameters for LightGBM/XGBoost rather than a full independent grid search for each; a more exhaustive tuning pass for the gradient-boosted candidates could change the specific numbers in Section 5, though it would need to close an 8+ point PR-AUC gap to change the conclusion.
