# Limitations

- Data is synthetic. Held-out metrics demonstrate a functioning evaluation path, not production performance.
- **The model has a structural recall ceiling of roughly 35% (temporal test) / 37% (cold-entity test), and this is understood, not accidental.** A diagnostic on the held-out test set found that 96.7% of fraud cases the model misses have zero physical evidence anomalies (matching SKU, matching serial, clean condition, verified warehouse scan) *and* minimal-to-no customer return history — statistically indistinguishable from a genuine first-time customer. This corresponds to the synthetic "behavioral" fraud archetype (~12% of all fraud cases by design), which intentionally carries no pre-refund signal. We tested whether engineered interaction features (e.g. refund-amount × merchant-risk, return-delay × customer-risk) could close this gap; they did not move recall meaningfully (34.5% → 35.3% on the temporal test) while measurably hurting precision at the same threshold. We conclude this ceiling reflects a genuine limit of pre-refund evidence-based detection rather than a fixable modeling gap — a real-world analogue is a first-time fraudster with a clean paper trail, who by definition cannot be caught by an evidence-based system before the fact.
  - **Practical implication**: this is a large part of why Reclaim Sentinel is architected as a multi-layer system rather than a single classifier. Deterministic rules catch physical-evidence fraud immediately regardless of ML score, and the coordinated-abuse graph engine and spike detector catch a different class of fraud (multi-account/device/address coordination) that doesn't depend on any single case's evidence quality. No single layer is expected to reach high recall alone.
  - **Merchant-configurable trade-off**: the locked threshold (0.35) is optimized to minimize total economic loss (false-positive cost + false-negative exposure), not to maximize recall. Merchants with lower fraud tolerance can choose a lower threshold — e.g. ~0.20 trades precision down to ~28% in exchange for recall up to ~45% on the temporal test — using the full trade-off table already exposed at `/api/evaluation` and on the Model Evaluation dashboard page.
- The baseline model is global rather than merchant-calibrated.
- The demo login is not production authentication.
- SQLite and in-memory indexes are suitable for a prototype, not a high-volume multi-tenant service.
- The graph view uses shared identifiers as supporting evidence; shared households or fulfillment centers can create legitimate links.
- The investigator is deterministic offline text generation. An optional LLM should be constrained to structured evidence and remain non-authoritative.
- Policy thresholds require review with merchant false-positive tolerance, refund economics, and customer-protection requirements.
- A real deployment needs signed audit events, retention policy, access logging, rate limiting, CSRF protection, schema validation at ingestion, and a production secret manager.
